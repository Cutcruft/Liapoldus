# ER-канвас редактора сайта (слайс R14, проектирование)

Статус: **утверждено** — решения зафиксированы (см. «Решения»), реализация идёт
(Фаза 5 в TODO.md; слайс R14 в `docs/redesign/spec.md` §8).

## Идея
Редактор сайта представлен **единым канвасом** (ER-диаграмма): узлы — сущности
сайта, рёбра — связи/биндинги. IDE-подобный редактор (`EditorPage`) остаётся:
он отвечает за код/вёрстку компонентов, контент и детальную настройку. Канвас —
главный вид для **структуры**: выстраивание страниц, роутов, компонентов и
источников данных и их связей, минуя форму-в-форме.

Канвас заменяет создание роутов и страниц «через заход в редактор» (Инфраструктуру
и list-страницы): страницу создают и вешают на роут прямо на канвасе, в IDE
заходят только чтобы вёрстать/настраивать.

## Решения
1. **MVP — 5 типов узлов сразу**: домен→роут→страница→компонент→источник данных.
2. **Канвас — единственный путь** для создания роутов/страниц: с MVP убираем
   старые `SiteRoutesPage`/`SitePagesPage` и legacy-роуты из прода (в dev — fallback).
3. **Авто-layout (dagre)** для первоначальной раскладки; дальше вручную.
4. **Tiptap отменён** — лист-примитив = `nodeType` + только TS-скрипт
   (обычное код-поле, без slash-команд).

## Узлы (сущности)
- **Домен** — host (например `example.com`).
- **Роут** — matcher (регэксп), приоритет; рендерит страницу.
- **Страница** — минимум: `имя + slug + каркас (layout)`. Контент/вёрстка — в IDE.
- **Компонент** (custom) — регистр существующий; лист-нода-«примитив» =
  `nodeType + ts-скрипт` (без schema/пропсов).
- **Источник данных** — коллекция контента (`Content`, `listContents`) для MVP;
  операции/эндпоинты/формы (инфраструктура) — следующий слайс (R11).

## Рёбра (связи/биндинги)
- `домен → роут` (host)
- `роут → страница` (`renderPage`)
- `страница → компоненты` (bind по пропсу)
- `компонент → источник данных` (биндинг данных)

## Графический стек
- **@xyflow/react (React Flow)** — ноды/эджи, зум/пан, мини-карта, экспорт JSON.
- **shadcn/ui** — панели, формы создания узлов, тулбары, инспектор.
- **Tiptap** — *не нужен*: «скрипты/команды» тут не редактор текста, а
  лист-ноды-примитивы, чьё тело — только TS-скрипт (см. примитивы выше).
  Отменяем Tiptap и slash-команды.

## REST-стратегия
**Построчно в существующие ресурсы** (никакого отдельного graph-документа):
- Читаем всё и параллельно: `GET /api/sites/{siteId}` (hosts), `listRoutes`,
  `listPages`, `GET /api/sites/{siteId}/components` (registry), `listContents` →
  собираем граф на клиенте.
- Создание/удаление/обновление узла и ребра → `POST/PUT/DELETE` соответствующих
  существующих эндпоинтов (`createRoute`, `createPage`, `createContent`, ...).
Одна истина в данных: и админка, и канвас работают с теми же REST-ресурсами.

## Раскладка
- Позиции/зум узлов и порядок хранятся **в localStorage** (ключ по `siteId`).
  Backend не трогаем под раскладку.

## Реализация (этапы)
1. `admin` — установка `@xyflow/react` и shadcn-компонентов (dialog, dropdown, input,
   select, tooltip, badge).
2. Хук `useSiteGraph(siteId)`: parallel-fetch доменов/роутов/страниц/компонентов/источников
   → типизированные узлы+рёбра React Flow.
3. Kanvas `SiteGraphCanvas` + `.nodeTypes` (DomainNode, RouteNode, PageNode,
   ComponentNode, SourceNode) и `.edgeTypes` по видам связей.
4. Инспектор выбранного узла (shadcn sheet): форма полей + кнопка «Открыть в IDE»
   (для страницы/компонента) и переиспользуемые редакторы (маршрут/токены).
5. Создание узла из палитры/правого клика → shadcn dialog → POST ресурса → авто-лейаут
   на свободное место; раскладка в localStorage.
6. Связь через React Flow handles + валидация типов (нельзя роут→компонент и т.п.).
7. `InfraSection` список не удаляем сразу: канвас — новое представление; старый CRUD
   оставляем как fallback (dev), пока канвас не закроет весь путь.
8. Тесты: unit (map REST→граф, маршрутизация рёбер, localStorage layout поворачивает),
   component (создание ноды, инспектор, примитив-лист).
